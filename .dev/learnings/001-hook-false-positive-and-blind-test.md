# 001. 훅 테스트가 거짓 통과했고, 훅이 따옴표 안 문자열까지 막았다

- 날짜: 2026-11-05
- 관련 파일: `.claude/hooks/block-dangerous-git.sh`, `.claude/hooks/test-block-dangerous-git.sh`, `.claude/settings.json`

## AI가 틀린 것

### 1) 실행되지 않은 테스트를 결과로 읽을 뻔함
- `chmod +x .claude/hooks/block-dangerous-git.sh`가 샌드박스 쓰기 제한으로 실패했는데, AI는 그대로 테스트를 이어갔다.
- 실행 권한이 없는 스크립트를 직접 호출해서, 막아야 할 명령 11개가 전부 `exit=0`으로 나왔다. 훅이 아니라 테스트가 고장 난 상태였다.
- 과제 4-4의 경고("훅은 잘못 만들어도 에러 없이 그냥 통과한다")가 테스트 쪽에서 그대로 일어났다.

### 2) 훅이 명령이 아닌 문자열까지 막음 (오탐)
- 첫 버전은 명령 텍스트 전체에서 `git push` 패턴을 찾았다.
- 그래서 AI가 테스트 케이스를 따옴표 안에 넣어 실행하려던 명령(`git commit -m "docs: git push 안내"`, `grep -n "git push" ...`)까지 차단됐다.
- 이 방식이면 5-6주차에 "push 규칙 문서 수정" 같은 정상 커밋도 막힌다.

## 고친 방법
1. 훅 호출을 `bash "$CLAUDE_PROJECT_DIR"/.claude/hooks/...`로 바꿨다. 실행 권한(`chmod`)에 의존하지 않는다.
2. 검사 전에 따옴표 안 문자열을 제거한다. 단 `bash -c`, `sh -c`, `eval`은 따옴표 안이 실제 명령이라 원문 그대로 검사한다.
3. `&&`, `||`, `;`, `|`, 줄바꿈으로 명령을 쪼개고, 각 명령의 맨 앞이 `git ... push`인지 본다.
4. 테스트는 기대값과 실제 exit code를 비교해서 `OK/FAIL`과 `PASS/FAIL` 개수를 출력한다. 차단 케이스와 통과 케이스를 둘 다 넣는다. (26개 전부 통과)
5. 마지막으로 실제 세션에서 `git push --dry-run`을 시도해 차단 메시지를 확인했다.

## 규칙으로 승격한 것
- CLAUDE.md 작업 방식: "완료라고 말하기 전에 확인한다. 실행하지 못했다면 그렇다고 말한다."
- 훅을 고치면 차단 케이스와 통과 케이스를 모두 테스트하고, 기대값과 비교한 결과(OK/FAIL)를 보고한다.

## 이후 변경 (같은 날)
- 정책 변경: GitHub 쓰기 금지(일반 push, `gh pr/issue create` 등)를 CLAUDE.md, rules, 훅에서 모두 제거했다. 훅은 되돌리기 어려운 명령(`git push --force`, `reset --hard`, `clean -f`, `branch -D`, 작업 트리 전체 되돌리기)만 막는다.
- 이때 추가로 발견: `bash -c`/`sh -c`/`eval` 안쪽 명령 검사가 push 패턴에만 따로 있어서, `sh -c 'git reset --hard'`는 통과하고 있었다. 감싼 명령은 접두어를 벗겨서 모든 패턴으로 검사하도록 고쳤다.
- 테스트도 새 정책에 맞게 다시 만들었다. 차단 13개 + 통과 13개(일반 push, `gh pr create` 포함), 26개 전부 통과.
- 교훈: 정책을 바꾸면 "막던 것"만 지우지 말고, 남은 패턴이 모든 경로(감싼 명령 포함)에 적용되는지 테스트로 다시 확인한다.

## 재검토 (같은 날, PR 전 리뷰)

### 검증이 애매했던 이유
- 실제 세션 검증(`git push --dry-run` 차단 확인)은 정책 변경 **이전** 것이었다. 정책 변경 후 일반 push는 막지 않으므로, 바뀐 훅을 실제 세션에서 확인한 기록이 없었다.
- "26개 전부 통과"의 테스트는 즉석 명령으로 돌리고 저장하지 않아서, 누구도 다시 실행해 확인할 수 없었다.
- 훅 첫 줄이 `#!/bin/bash되돌리기 어려운 git 명령`으로 주석과 붙어 깨져 있었다. `bash 스크립트`로 호출해서 동작은 했지만, 편집 후 파일을 다시 확인하지 않았다는 신호였다.

### 새로 발견한 문제
- **fail-open**: jq가 없거나 JSON 파싱에 실패하면 `COMMAND`가 빈 값이 되어 `exit 0`으로 조용히 통과했다. `settings.json`은 팀이 공유하므로, jq가 없는 PC에서는 경고 없이 보호가 사라진다. 따옴표 제거와 명령 분리에 쓰는 perl도 같은 문제였다.
- **오탐**: `git restore --staged .`(스테이징 취소, 작업 트리는 그대로)까지 "작업 트리 전체 되돌리기"로 막았다.

### 고친 방법
1. fail-closed: jq, perl이 없거나 JSON 파싱에 실패하면 `exit 2`로 막고 원인을 출력한다. `command` 필드가 없는 입력은 검사할 명령이 없으므로 통과한다.
2. `restore .` 검사에서 `--staged`/`-S`만 쓴 경우는 통과시킨다. `--worktree`/`-W`/`-SW`가 함께 있으면 계속 막는다.
3. 테스트를 `.claude/hooks/test-block-dangerous-git.sh`로 레포에 남겼다. 차단 19 + 통과 11 + fail-closed 3 = 33개, `PASS=33 FAIL=0`.
4. 테스트가 가짜 통과가 아닌지 확인했다.
   - jq 없음 케이스의 exit 2가 의도한 메시지(`jq가 설치되어 있지 않아요`)에서 나온 것인지 stderr로 확인했다.
   - `--hard` 패턴을 일부러 망가뜨린 사본에서 `git reset --hard`가 exit 0으로 통과하는 것을 보고, 테스트가 회귀를 잡아낸다는 것을 확인했다.
5. 정책 변경 후 실제 세션에서 다시 확인했다. `git branch -D <없는 브랜치>`는 차단 메시지와 함께 막혔고, `git commit --dry-run -m "... git branch -D ..."`와 `git restore --staged <경로>`는 통과했다.
   - 실패해도 피해가 없는 명령(존재하지 않는 브랜치, dry-run)으로만 시험했다.
   - `git restore --staged .`는 스테이징을 전부 풀어서 실제 세션에서는 실행하지 않고, 파이프 테스트로만 확인했다.

### 교훈
- 테스트는 저장해서 다시 돌릴 수 있어야 검증이다. 대화 속 "N개 통과"는 근거가 되지 못한다.
- 안전장치는 검사하지 못하는 상황에서 통과가 아니라 차단으로 끝나야 한다. (fail-closed)
- 훅을 바꾸면 파이프 테스트와 별개로 실제 세션에서 차단 1건, 통과 1건을 다시 확인한다.

## 남은 한계
- 문자열 기반 검사라서 변수 조합(`F=--force; git push $F`) 같은 우회는 못 막는다. 훅은 실수를 막는 안전장치이지 보안 경계가 아니다.
- 재검토에서 확인했지만 막지 않기로 한 우회:
  - `git -c x=y push --force`, `git --no-pager push -f`: push 패턴이 `-C` 외의 git 전역 옵션을 허용하지 않는다.
  - `env git ...`, `/usr/bin/git ...`, `GIT_DIR=x git ...`: 명령이 `git`으로 시작할 때만 검사한다.
  - `git reset "--hard"`, `echo "$(git reset --hard)"`: 따옴표를 제거할 때 옵션이나 명령까지 같이 사라진다.
  - `git push origin +main`: `+refspec` 형태의 force push.
  - `git checkout .`: `git checkout -- .`과 효과가 같은데 막지 않는다.
- 남은 오탐: `git commit -F - <<EOF` 본문에 금지 명령 문구가 있으면 heredoc 본문의 줄도 명령으로 검사해서 막는다. (`-m "$(cat <<'EOF' ...)"` 형태는 따옴표 안이라 통과)
