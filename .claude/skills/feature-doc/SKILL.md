# 기능 문서 작성

PR 하나당 `docs/features/`에 md 문서 1개를 만든다. 사람과 AI가 나중에 이 기능의 맥락을 다시 읽을 수 있게 하는 기록이다.

## 절차
1. 이슈 번호와 작업명을 정한다.
    - 사용자가 `/feature-doc 12 applicant-api`처럼 값을 넘겼다면 그 값을 쓴다: $ARGUMENTS
    - 없으면 브랜치 이름과 최근 커밋 메시지에서 추측하고, 사용자에게 확인받는다.
2. 기준 브랜치를 정한다. 4주차 이후라면 `이름/basic`, 1~3주차 방식이라면 `develop`이다. 모르면 사용자에게 묻는다.
3. `git diff --stat <기준브랜치>...HEAD`와 `git log --oneline <기준브랜치>..HEAD`로 변경 범위를 파악한다.
4. 변경된 Controller에서 API 목록(메서드, URL, 요청/응답 DTO)을 뽑고, 관련 `ErrorCode`에서 에러 케이스를 뽑는다.
5. `references/template.md` 형식에 맞춰 `docs/features/이슈번호-작업명.md`를 작성한다.
6. 코드만으로 알 수 없는 내용은 비워두지 말고 사용자에게 질문한다.
    - 배경(왜 필요했는지), 설계 결정(다른 선택지와 고른 이유), 검증 방법
7. 작성한 파일 경로와 질문으로 채운 부분을 짧게 보고한다.

## 하지 말 것
- 코드를 수정하지 않는다. 문서만 쓴다.
- 배경이나 설계 이유를 지어내지 않는다.
- commit이나 push를 하지 않는다.
- 이미 같은 이름의 문서가 있으면 덮어쓰지 말고 사용자에게 먼저 묻는다.
