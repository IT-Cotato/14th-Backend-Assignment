# 기능 문서 작성

## 절차

1. 사용자에게 이슈 번호와 작업명을 묻는다. 이미 대화에서 알 수 있으면 확인만 받는다.
2. 이번 작업에서 추가되거나 변경된 파일을 확인한다.
   Git 명령은 사용하지 않는다. 대화 내용과 파일 읽기로 파악하고,
   불확실하면 사용자에게 어떤 파일을 작업했는지 묻는다.
3. 아래 형식에 맞춰 내용을 채운다. 비어 있는 항목은 사용자에게 질문해서 채운다.
4. `docs/features/<이슈번호>-<작업명>.md` 경로로 파일을 만든다.
   작업명은 영문 소문자와 하이픈으로 쓴다. (예: `7-book-crud.md`)
5. 작성한 내용을 사용자에게 보여주고, 수정할 부분이 있는지 확인받는다.

## 문서 형식

    # 기능 이름

    - 이슈: #이슈번호
    - PR: (PR 링크)
    - 작성일: YYYY-MM-DD

    ## 배경
    (왜 이 기능이 필요했는지)

    ## 구현 내용
    (무엇을 만들거나 바꿨는지, 주요 클래스와 흐름)

    ## API 명세
    (메서드와 URL, 요청, 응답, 에러 케이스를 표로 정리)

    ## 설계 결정
    (왜 이렇게 했는지, 고민했던 다른 선택지)

    ## 검증
    (어떻게 확인했는지: Swagger 호출 결과, 테스트 등)

    ## 남은 이슈
    (아직 못 한 것, 다음에 할 것)

## 작성 기준

- 코드를 그대로 붙여넣지 않는다. 무엇을 왜 했는지를 글로 설명한다.
- API 명세는 표로 정리한다. 메서드, URL, 요청 본문, 응답, 에러 코드를 포함한다.
- 에러 케이스는 `ErrorCode`에 정의한 코드와 상태를 그대로 적는다.
- 설계 결정에는 고민했던 다른 선택지도 함께 적는다. 결과만 적으면 나중에 이유를 알 수 없다.
- 검증 항목은 "확인함"이 아니라 무엇을 어떻게 확인했는지 구체적으로 적는다.

## 하지 말 것

- 확인하지 않은 내용을 추측해서 채우지 않는다. 모르는 항목은 사용자에게 묻는다.
- Git 명령을 실행하지 않는다.
- 소스 코드를 수정하지 않는다. 문서만 작성한다.
