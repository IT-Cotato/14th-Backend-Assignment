# #129 스터디 매칭 핵심 기능 (인증 / 모집글 / 댓글)

PRD(`docs/PRD.md`) 3장 작업순서 0~4단계(모노레포 세팅 → 인증 → 모집글 → 댓글 → E2E)를 구현한 기능 문서. API 필드/에러코드의 전체 명세는 `docs/api-spec.md`를 참고하고, 이 문서는 **구현 과정에서의 주요 결정사항과 가정**을 중심으로 정리한다.

## 1. 인증

### 구현 내용
- `User` 엔티티(테이블 `users`, MySQL 예약어 회피), `Part` enum(PM/DE/BE/FE, `EnumType.STRING`)
- JWT 발급/검증(`jjwt` 0.12.6), 로그아웃 토큰 블랙리스트, soft-auth 필터(토큰이 있으면 공개 API에서도 인증 정보를 채움)
- API: `POST /api/auth/signup`, `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/users/me`

### 주요 결정사항 (PRD에 없는 세부 규칙 → "쉬운 쪽")
- JWT 라이브러리: `io.jsonwebtoken:jjwt-*` (PRD 기술스택 표가 "JWT"만 명시, 생태계 표준 선택이라 추가 사유만 기록)
- 토큰 블랙리스트 저장: 인메모리(`ConcurrentHashMap`). 서버 재시작 시 초기화되는 트레이드오프 있음(DB 테이블로 바꿀 수 있음)
- JWT 만료시간 1시간, 인증 principal은 커스텀 `UserDetails` 없이 `Long userId`를 그대로 사용
- 로그인/회원가입 성공 후 이동 경로: 회원가입→`/login`(PRD 그대로), 로그인→`/studies`(모집글 화면이 2단계에서 생기므로 1단계에선 `/mypage`로 임시 처리했다가 2단계에서 PRD대로 교정)

### 테스트
`UserServiceTest`, `AuthServiceTest`, `JwtTokenProviderTest` (Mockito 단위 테스트, DB 없이 실행)

## 2. 모집글

### 구현 내용
- `StudyPost` 엔티티(`user` LAZY FK, `studyStatus` enum STRING), `StudyStatus`(RECRUITING/CLOSED)
- 목록: 키워드(제목+내용)/모집상태/파트 필터, 페이지네이션, 최신순. `author`+`commentCount` 접근에서 N+1 방지(JOIN FETCH 1회 + 배치 COUNT 1회)
- 상세: 공개 API지만 토큰이 있으면 `isAuthor` 계산(soft-auth)
- 수정/삭제: 작성자 본인만(403 `NOT_POST_AUTHOR`)
- API: `POST/GET /api/study-posts`, `GET/PATCH/DELETE /api/study-posts/{postId}`

### 주요 결정사항
- `author`(`nickname,generation,part`) DTO는 `domain/user`에 둬서 3단계(댓글)에서도 재사용
- 페이지네이션 공통 DTO `PageResponse<T>`는 `global/common/response`에 둬서 모집글/댓글이 공유
- create/update 응답이 둘 다 `{postId}`라 `StudyPostIdResponse` 하나 공유(이 레포 첫 응답 DTO 공유 사례)
- `StudyPost`에 `updateTitle/updateContent/updateStatus` mutator 추가(이 레포 첫 엔티티 mutator, PATCH 부분수정의 dirty-checking 때문)

### 발견한 버그
- 응답 DTO에 `author`(객체) 필드와 boolean `isAuthor` 필드가 같이 있으면, boolean getter를 `isAuthor()`로 두는 순간 Jackson이 "author" 프로퍼티로 오인해 `author` 객체를 응답에서 통째로 지워버림. `getIsAuthor()` + `@JsonProperty("isAuthor")`로 수정(댓글 쪽에도 처음부터 동일하게 적용).

### 테스트
`StudyPostServiceTest`(Mockito, 17개). N+1은 자동 테스트 대신 `show-sql` 로그를 수동으로 확인(목록 조회 시 쿼리 수가 글 개수와 무관하게 고정됨을 확인).

## 3. 댓글 (= 스터디 신청)

### 구현 내용
- `StudyPostComment` 엔티티(`studyPost`+`user` 둘 다 LAZY FK)
- 작성: 로그인 필요, CLOSED 글엔 작성 불가(409 `STUDY_POST_CLOSED`)
- 목록: 공개, 오래된 순, soft-auth `isAuthor`
- 수정/삭제: 작성자 본인만(403 `NOT_COMMENT_AUTHOR`)
- 모집글 삭제 시 댓글도 함께 삭제: `@OneToMany` cascade 대신(이 레포에 전례 없음) `commentRepository.deleteByStudyPostId(postId)`를 명시적으로 호출
- API: `POST/GET /api/study-posts/{postId}/comments`, `PATCH/DELETE /api/comments/{commentId}`

### 주요 결정사항
- 라우트가 `/api/study-posts/{postId}/comments`(작성/목록)와 `/api/comments/{commentId}`(수정/삭제)로 베이스가 달라, 컨트롤러를 2개(`StudyPostCommentController`, `CommentController`)로 분리(이 레포의 "컨트롤러당 베이스 경로 1개" 컨벤션 유지)
- 프론트: 댓글 전용 라우트 없이 `/studies/:id` 상세 화면에 `CommentSection` 컴포넌트로 내장(PRD 화면표에 댓글 전용 경로가 없음), 수정은 인라인 토글로 처리

### 테스트
`CommentServiceTest`(Mockito, 14개) + `StudyPostServiceTest`에 댓글 리포지토리 모킹/cascade 검증 추가.

## 4. E2E 테스트

`frontend/e2e/{auth,study-post,comment}.spec.ts` — PRD 8장이 요구하는 정상+에러 시나리오 15개(인증 6, 모집글 5, 댓글 4). `getByRole`/`getByLabel`/`getByText`만 사용, 고정 대기 없음, 테스트마다 uuid 기반 독립 데이터, 비밀번호 코드 비하드코딩, 버튼 숨김 동작(남의 글/댓글 수정 등)은 `request` fixture로 API 직접 호출해 403/409 확인.

## 커밋
`sinyeong/monorepo` 브랜치에 작업순서(0~4단계)대로 5개 커밋. 0~3단계는 사용자 요청으로 백엔드+프론트+테스트를 하나로 묶어 커밋했고(PRD의 프로덕션/테스트 분리 권장과 다름, 매 단계 사전 확인받음), 4단계(E2E)는 프로덕션 코드 변경이 없어 테스트 코드만 담은 단독 커밋으로 PRD 규칙을 그대로 지켰다.
