# 126 코테이토 스터디 매칭 플랫폼

코테이토 스터디 신청을 네이버 카페에서 전용 플랫폼으로 옮기기 위해, 가장 핵심적인 기능만 골라 백엔드와 프론트엔드로 함께 만들었다. 별도의 가입 신청 기능은 없고, **모집글에 댓글을 남기는 것이 곧 스터디 신청**이다.

- 이슈: #126
- ERD: [ERDCloud](https://www.erdcloud.com/d/ua8yoNMr496mMjK6p), 이미지와 테이블 설명은 [docs/erd](../erd/README.md)
- API 명세: [docs/api-spec.md](../api-spec.md) (총 13개)

구현한 순서대로 인증, 모집글, 댓글을 정리한다.

## 공통

### 응답과 에러

성공 응답은 `ApiResponse`로 감싸고, 본문이 없는 `204`는 감싸지 않는다. 실패는 모든 API가 같은 `ErrorResponse`(`success`, `status`, `code`, `message`, `method`, `path`, `timestamp`)로 내려간다. 에러는 `Backend14thException(ErrorCode.XXX)`를 던지면 `GlobalExceptionHandler`가 변환한다.

| HTTP | ErrorCode | code | 언제 |
| --- | --- | --- | --- |
| 400 | `INVALID_INPUT` | COMMON-003 | 입력 검증 실패, `status=abc` 같은 잘못된 쿼리 값, 잘못된 페이지 값 |
| 401 | `UNAUTHORIZED` | COMMON-004 | 토큰이 없거나 무효이거나 로그아웃한 토큰 |
| 401 | `INVALID_CREDENTIALS` | USER-002 | 이메일 또는 비밀번호가 틀림 |
| 403 | `NOT_POST_AUTHOR` | STUDY-002 | 남의 모집글을 수정·삭제 |
| 403 | `NOT_COMMENT_AUTHOR` | COMMENT-002 | 남의 댓글을 수정·삭제 |
| 404 | `STUDY_POST_NOT_FOUND` | STUDY-001 | 없는 모집글 |
| 404 | `COMMENT_NOT_FOUND` | COMMENT-001 | 없는 댓글 |
| 409 | `EMAIL_ALREADY_EXISTS` | USER-001 | 이미 가입된 이메일 |
| 409 | `STUDY_POST_CLOSED` | STUDY-003 | 마감된 모집글에 댓글 작성 |

`status=abc`처럼 Enum으로 바꿀 수 없는 쿼리 값은 원래 500으로 떨어지므로, `MethodArgumentTypeMismatchException`을 잡아 400으로 돌려주도록 처리기를 추가했다.

### 계층 구조

Controller는 요청·응답 변환만 하고, 비즈니스 규칙과 트랜잭션은 Service에 둔다. 엔티티는 응답으로 직접 내보내지 않고 DTO로 바꿔서 내보낸다. 연관관계는 모두 `LAZY`, Enum은 문자열로 저장한다.

### 권한

조회(목록, 상세, 댓글 목록)는 누구나 가능하고, 작성은 로그인한 사용자, 수정·삭제는 작성자 본인만 가능하다. 공개 경로는 `SecurityConfig`에서 열어 두고, 나머지는 인증을 요구한다. 상세와 댓글 목록은 공개이지만, 토큰이 있으면 "내 글인지"를 알려 주기 위해 `@AuthenticationPrincipal`로 사용자 id를 받는다. 로그인하지 않았으면 이 값이 `null`이라 `isAuthor`는 `false`가 된다.

## 1. 인증

### 백엔드 (API 1~4번)

| API | 설명 |
| --- | --- |
| `POST /api/auth/signup` | 기수·파트를 포함해 가입. 비밀번호는 BCrypt로 암호화해서 저장 |
| `POST /api/auth/login` | 이메일·비밀번호 확인 후 JWT `accessToken` 발급 |
| `POST /api/auth/logout` | 사용한 토큰을 만료 시각까지 무효 처리 |
| `GET /api/users/me` | 내 정보 조회. 비밀번호는 응답에 넣지 않음 |

- 입력 검증은 이메일 형식, 비밀번호 8자 이상, 닉네임 2~10자, 기수 1 이상, 파트는 `PM`·`DE`·`BE`·`FE` 중 하나다.
- 토큰은 JWT(jjwt)이고 유효 시간은 기본 1시간이다. 시크릿과 유효 시간은 환경변수(`JWT_SECRET`, `JWT_EXPIRATION_MS`)로 받는다.
- 요청마다 `JwtAuthenticationFilter`가 `Authorization: Bearer` 토큰을 확인해 사용자 id를 인증 정보로 넣는다. 토큰이 없거나 무효이면 `JwtAuthenticationEntryPoint`가 공통 `ErrorResponse` 형식으로 401을 내려준다.
- **로그아웃은 서버 메모리에 로그아웃한 토큰을 보관하는 방식**이다(`TokenBlacklist`). 토큰은 만료 시각이 지나면 어차피 쓸 수 없으므로 만료된 항목은 새로 등록할 때 함께 지운다. 구현이 간단한 대신 서버를 재시작하면 목록이 사라져, 재시작 전에 로그아웃한 토큰이 다시 유효해지는 한계가 있다. DB나 Redis에 저장하면 해결되지만 이번 범위에서는 쉬운 쪽을 택했다.

### 프론트엔드

- 회원가입(`/signup`): 서버와 같은 규칙으로 먼저 검사해서 항목별 메시지를 보여 주고, 성공하면 로그인 화면으로 이동한다.
- 로그인(`/login`): 성공하면 토큰을 저장하고 목록으로 이동한다. 실패하면 서버가 내려준 메시지를 보여 준다.
- 마이페이지(`/mypage`): 이메일, 이름, 닉네임, 기수, 파트를 보여 준다.
- 헤더는 로그인 상태에 따라 달라진다. 로그인 전에는 로그인·회원가입, 후에는 닉네임·마이페이지·로그아웃이 보인다.
- `AuthProvider`가 저장된 토큰으로 내 정보를 불러와 앱 전체에 나눠 준다. `ProtectedRoute`는 로그인이 필요한 화면에 로그인 없이 들어오면 로그인 화면으로 보낸다.
- axios 요청 인터셉터가 토큰을 헤더에 붙이고, **토큰을 보냈는데 401이 오면** 토큰을 지우고 로그인 화면으로 보낸다. 토큰 없이 보낸 로그인 요청의 401("비밀번호가 틀림")은 건드리지 않는다.

## 2. 스터디 모집글

### 백엔드 (API 5~9번)

| API | 설명 |
| --- | --- |
| `POST /api/study-posts` | 작성. 처음 상태는 항상 `RECRUITING` |
| `GET /api/study-posts` | 목록. 키워드, 모집 상태, 작성자 파트로 거르고 최신순, 페이징 |
| `GET /api/study-posts/{postId}` | 상세. 내 글이면 `isAuthor: true` |
| `PATCH /api/study-posts/{postId}` | 수정. 바꿀 필드만 보내면 되고 모집 상태도 여기서 바꿈 |
| `DELETE /api/study-posts/{postId}` | 삭제. 달린 댓글도 함께 삭제 |

- **목록 검색**은 JPQL 한 개로 처리한다. 값이 `null`인 조건은 무시하고(`:keyword is null or ...`), 파트는 작성자(`User`)의 값이라 `join`한다. 조건을 여러 개 주면 모두 만족하는 글만 나온다. 정렬은 `createdAt desc, id desc`로, 같은 시각에 만든 글도 순서가 흔들리지 않게 했다. 공백뿐인 키워드는 조건으로 쓰지 않는다.
- **N+1을 피하려고** 목록과 상세에서 작성자를 `join fetch`로 한 번에 가져오고, 목록 개수를 세는 `countQuery`는 따로 둔다. 글마다 댓글 수는 글 번호 목록을 한 번에 넘겨 `group by`로 센다(글마다 따로 세면 쿼리가 글 수만큼 늘어난다).
- 수정은 `PATCH`라서 보낸 값(`null`이 아닌 값)만 바꾼다. 값이 있으면 길이 규칙(제목 1~50자, 내용 1~2000자)을 지켜야 한다. 존재하지 않는 글이면 404를, 작성자가 아니면 403을 돌려준다.
- 삭제는 먼저 댓글을 한 번의 `delete` 쿼리로 지우고 글을 지운다. 둘은 같은 트랜잭션이라 중간에 실패하면 함께 되돌아간다.
- 상세 응답의 `isAuthor`는 `Boolean` 필드로 두었다. Lombok이 `boolean isAuthor`에서 만드는 getter(`isAuthor()`)는 JSON 이름이 `author`가 되어 명세의 `author` 객체와 충돌하기 때문이다.
- 페이지 값이 잘못되면(`page < 0`, `size < 1` 또는 `size > 100`) 400을 돌려준다. 너무 큰 `size`로 한 번에 많이 가져가는 것을 막기 위해서다.

### 프론트엔드

- 목록(`/studies`): 키워드 검색, 모집 상태 필터, 파트 필터, 이전/다음 페이지 이동. 각 글에 모집 상태, 작성자 닉네임·기수·파트, 작성일, 댓글 수를 보여 준다. 로그인했을 때만 "글쓰기" 버튼이 보인다. 검색 조건은 주소(`?keyword=...&status=...&page=...`)에 담아서 새로고침하거나 뒤로 가도 유지된다. 필터를 바꾸면 첫 페이지부터 다시 본다.
- 상세(`/studies/:postId`): 내용(줄바꿈 유지)과 댓글 영역. 작성자에게만 "모집 마감하기"(마감 후에는 "모집 다시 열기"), "수정", "삭제"가 보인다. 삭제는 확인창을 한 번 거친다.
- 작성·수정(`/studies/new`, `/studies/:postId/edit`): 하나의 화면 컴포넌트를 함께 쓴다. 수정 화면은 기존 내용을 불러오고, 제목·내용과 함께 **모집 상태**(모집 중 / 모집 마감)도 바꿀 수 있다. 내 글이 아니면 상세 화면으로 돌려보낸다. 로그인하지 않으면 로그인 화면으로 간다.

## 3. 댓글 (스터디 신청)

### 백엔드 (API 10~13번)

| API | 설명 |
| --- | --- |
| `POST /api/study-posts/{postId}/comments` | 작성. 마감된 글이면 409 |
| `GET /api/study-posts/{postId}/comments` | 목록. 오래된 순, 기본 `size`는 20 |
| `PATCH /api/comments/{commentId}` | 수정. 작성자만 |
| `DELETE /api/comments/{commentId}` | 삭제. 작성자만 |

- 작성할 때는 글이 있는지(404), 마감되지 않았는지(409)를 차례로 확인한다. 같은 사람이 여러 번 달 수 있다.
- 목록 응답의 `isAuthor`는 요청한 사용자가 쓴 댓글인지를 뜻한다. 로그인하지 않았으면 모두 `false`다.
- 없는 글의 댓글 목록은 빈 목록이 아니라 404(`STUDY_POST_NOT_FOUND`)다.
- 요청 DTO(`CommentRequest`)는 작성과 수정에 함께 쓰고, 1~500자를 검증한다.

### 프론트엔드

상세 화면 아래에 댓글 영역이 붙는다.

- 로그인하지 않았으면 댓글은 읽을 수 있고, 입력창 대신 "댓글을 쓰려면 로그인이 필요해요" 안내가 보인다.
- 로그인했으면 "신청 댓글" 입력창이 보이고, 등록하면 새 댓글이 보이는 마지막 페이지로 이동한다.
- 내 댓글에만 "수정", "삭제"가 보인다. 수정은 그 자리에서 입력창으로 바뀌고, 삭제는 확인창을 거친다.
- 모집이 마감된 글에는 입력창 대신 "모집이 마감된 글에는 댓글을 쓸 수 없어요"가 보인다.

## 테스트: Playwright E2E

`frontend/e2e/`에 화면 → 프론트 → API → DB 전체 흐름을 확인하는 테스트 32개가 있다(인증 7, 모집글 13, 댓글 7, 권한 5).

- 요소는 `getByRole`, `getByLabel`, `getByText`로 찾고, `waitForTimeout` 같은 고정 대기는 쓰지 않는다. `expect`가 조건이 맞을 때까지 기다린다.
- 테스트마다 독립이다. 이메일(`e2e-`로 시작), 닉네임, 글 제목을 매번 새로 만들고, 비밀번호는 코드에 적지 않고 실행할 때마다 무작위로 만든다.
- 준비 단계(계정, 글, 댓글 만들기)는 API로 빠르게 하고, 확인하려는 동작은 화면으로 한다.
- 각 기능마다 정상과 에러 시나리오를 함께 둔다. 예를 들어 이미 가입된 이메일, 기수 0 입력, 틀린 비밀번호, 로그인 없이 마이페이지 접근, 빈 제목, 남의 글의 수정·삭제 버튼 숨김과 수정 주소 차단, 마감된 글에 댓글 쓰기 불가, 남의 댓글 수정·삭제 버튼 숨김 등이다.
- 화면에서 버튼을 숨긴 동작은 서버도 정말 막는지 API를 직접 호출해서 따로 확인한다(`permissions.spec.ts`). 토큰 없이 쓰기 401, 남의 글·댓글 수정·삭제 403, 마감된 글에 댓글 409, 로그아웃한 토큰 401이다.
- 테스트가 같은 DB를 쓰므로 `workers: 1`로 한 번에 하나씩 돌린다.

실행 순서는 이렇다. 먼저 MySQL과 백엔드(8080번)를 켠 뒤, `frontend/`에서 아래를 실행한다. 프론트 개발 서버(3000번)는 Playwright가 필요하면 띄운다.

```bash
npx playwright test
```

설정은 컴퓨터에 설치된 Chrome을 쓴다(`channel: 'chrome'`). Chrome이 없으면 `playwright.config.ts`의 `channel` 줄을 지우고 `npx playwright install chromium`을 먼저 실행한다. 테스트 데이터는 개발 DB에 남는다. 이메일이 `e2e-`로 시작하므로 직접 만든 데이터와 구분할 수 있다.
