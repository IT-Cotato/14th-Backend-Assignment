# #140 코테이토 스터디 매칭 플랫폼 (인증 · 모집글 · 댓글)

네이버 카페에서 하던 스터디 신청을 대신할 스터디 매칭 플랫폼을 만들었어요.
`docs/api-spec.md`의 API 13개를 백엔드(Spring Boot)로 구현하고, 프론트엔드(React)로 화면을 만들었어요. Playwright E2E 테스트도 붙였어요.

- 관련 문서: `docs/api-spec.md`(API 명세와 명세 변경 기록), `docs/erd/README.md`(테이블)
- 하네스: `.claude/rules/e2e.md`(E2E 규칙)

## 한눈에 보기

| 기능 | API | 화면 |
|---|---|---|
| 인증 | 1 회원가입, 2 로그인, 3 로그아웃, 4 내 정보 | `/signup`, `/login`, `/mypage`, 헤더 |
| 모집글 | 5 작성, 6 목록(검색·필터·페이징), 7 상세, 8 수정(마감 포함), 9 삭제 | `/studies`, `/studies/:id`, `/studies/new`, `/studies/:id/edit` |
| 댓글(= 스터디 신청) | 10 작성, 11 목록, 12 수정, 13 삭제 | `/studies/:id`의 댓글 영역 |

## 1. 인증

### 무엇을
- 이메일·비밀번호로 가입하고, 기수(`generation`, 1 이상)와 파트(`PM`, `DE`, `BE`, `FE`)를 입력해요.
- 로그인하면 JWT `accessToken` 하나를 받아요. 로그아웃하면 그 토큰을 만료 시각까지 쓸 수 없어요.
- 내 정보 화면(`/mypage`)에서 이메일·이름·닉네임·기수·파트를 봐요.

### 왜
- 모집글 작성과 댓글(신청)은 "누가" 했는지가 중요해서 로그인이 먼저 필요했어요.
- 기수·파트는 모집글 목록의 파트 필터와 작성자 정보(`14기 · BE`)에 쓰여요.

### 어떻게
**백엔드** (`domain/user`, `global/security`)
- `User` 엔티티: `BaseEntity` 상속, `email` 유니크, `part`는 `@Enumerated(STRING)`
- 비밀번호는 `BCryptPasswordEncoder`로 암호화해 저장하고, 응답 DTO(`UserResponse`)에는 넣지 않아요.
- JWT는 JJWT 0.12.6으로 만들어요. 시크릿과 만료 시간은 `backend/.env`(`JWT_SECRET`, `JWT_ACCESS_TOKEN_EXPIRATION`)에서 읽어요. `.env.example`에는 변수 이름만 있어요.
- `JwtAuthenticationFilter`: 토큰이 유효하고 블랙리스트에 없으면 SecurityContext에 `userId`를 넣어요. 토큰이 없거나 잘못돼도 여기서 막지 않고 넘겨요. 그래서 공개 API는 비로그인으로 동작하고, 로그인 API는 `JwtAuthenticationEntryPoint`가 401(`COMMON-004`)을 내려요.
- `SecurityConfig`: api-spec의 공개/로그인 권한대로 경로를 나눴어요. 3주차 CORS 연결은 그대로 두고, preflight(`OPTIONS`)는 인증 없이 통과시켜요.
- 로그인 실패는 이메일이 없을 때와 비밀번호가 틀릴 때 모두 같은 `INVALID_CREDENTIALS`(401)를 내려요. 어떤 이메일이 가입돼 있는지 드러나지 않게 하려고요.

**프론트엔드** (`src/api`, `src/auth`)
- `apiClient`(axios): 요청마다 토큰을 붙여요. 토큰을 실어 보낸 요청이 401이면 토큰을 지우고 `/login`으로 보내요. 로그인 실패(토큰 없이 보낸 요청의 401)는 이 처리에 걸리지 않고 화면에 서버 메시지가 떠요.
- `AuthProvider`: 새로고침하면 저장된 토큰으로 내 정보를 다시 불러와 로그인 상태를 복원해요. 로그인 응답에는 닉네임이 없어서 헤더에 닉네임을 보여주려면 이 과정이 필요해요.
- `RequireAuth`(로그인 필요한 화면), `GuestOnly`(로그인했으면 로그인·가입 화면 대신 `/studies`로)
- `FormField`: `label`과 입력창을 `htmlFor`/`id`로 연결하고, 에러는 `aria-describedby`로 연결해요. E2E가 `getByLabel`로 찾을 수 있어요.

## 2. 스터디 모집글

### 무엇을
- 모집글 작성·수정·삭제. 처음에는 `RECRUITING`이고, 작성자가 `CLOSED`(마감)와 `RECRUITING` 사이를 자유롭게 바꿔요.
- 목록: 키워드(제목+내용), 모집 상태, 작성자 파트 필터를 함께 쓸 수 있고, 최신순으로 페이징해요.
- 상세: 누구나 볼 수 있고, `isAuthor`로 작성자에게만 수정·삭제·마감 버튼을 보여줘요.

### 왜
- 네이버 카페 게시판을 대신하는 핵심 화면이에요. 같은 파트 사람을 찾는 경우가 많아서 파트 필터가 **작성자의 파트** 기준이에요.

### 어떻게
**백엔드** (`domain/studypost`)
- `StudyPost` → `User` `@ManyToOne(LAZY)`. 수정은 `update(title, content, studyStatus)`로 보낸 값(null이 아닌 값)만 바꿔요.
- 목록은 JPQL `@Query` 하나로 만들어요. `(:status is null or ...)`처럼 값이 없으면 그 조건을 건너뛰어요. 작성자는 `join fetch`로 같이 가져와서 N+1이 없어요.
- 권한 검사는 서비스에서 해요. 검사 순서는 항상 404 → 403이에요. 없는 글에 대해 작성자인지 아닌지를 말하지 않으려고요.
- 응답은 공통 `PageResponse`(content, page, size, totalElements, totalPages)와 `AuthorResponse`(nickname, generation, part)로 내려요. 둘 다 댓글에서도 써요.

**프론트엔드** (`src/pages/Studies*`, `src/components`)
- 목록의 검색어·필터·페이지는 URL 쿼리(`?keyword=&status=&part=&page=`)가 기준이에요. 새로고침하거나 뒤로 가도 유지돼요. URL에 잘못된 값이 있으면 무시하고 전체 / 1페이지로 봐요.
- 검색어는 검색 버튼이나 Enter로 적용하고, 상태·파트 필터는 고르면 바로 적용하면서 1페이지로 돌아가요.
- 남의 글 수정 화면(`/studies/:id/edit`)에 주소로 직접 들어오면 상세로 돌려보내고 "작성자만 수정할 수 있어요."를 보여줘요. 저장하더라도 서버가 403으로 한 번 더 막아요.
- 삭제는 `window.confirm`으로 확인을 받아요.

## 3. 댓글 (= 스터디 신청)

### 무엇을
- 모집글에 댓글을 달면 그게 곧 신청이에요. 같은 사람이 여러 번 달아도 돼요.
- 마감된 글에는 댓글을 쓸 수 없어요(409). 수정·삭제는 작성자만 할 수 있어요(403).
- 목록은 누구나 볼 수 있고, 오래된 순으로 페이징하며 `isAuthor`를 포함해요.
- 모집글을 지우면 달린 댓글도 함께 지워져요. 모집글 목록에는 댓글 수(`commentCount`)가 나와요.

### 왜
- 별도의 "신청" 기능 없이 댓글로 신청을 받는 게 기존 카페 방식과 같아서 익숙해요.
- 마감 후에는 신청을 막아야 하지만, 이미 단 신청 글을 고치거나 지우는 건 막을 이유가 없어서 명세대로 작성만 막았어요.

### 어떻게
**백엔드** (`domain/comment`)
- `StudyPostComment` → `StudyPost`, `User` 단방향 `@ManyToOne(LAZY)`. 모집글에는 댓글 컬렉션을 두지 않아요.
- 작성 검사 순서: 글 없음(404 `STUDY-001`) → 마감(409 `STUDY-003`) → 유저 없음(401)
- 모집글 삭제: `StudyPostService.delete`에서 **댓글 일괄 삭제 → 글 삭제** 순서로, 같은 트랜잭션에서 처리해요.
- `commentCount`: 목록 한 페이지의 글 id로 `group by` 쿼리를 한 번 실행해서 채워요. 댓글이 없는 글은 0이에요.

**프론트엔드** (`src/components/comments`)
- 상세 화면의 댓글 영역(`CommentSection`)에서 20개씩 불러오고, "댓글 더 보기"로 다음 20개를 아래에 붙여요.
- 작성 영역은 상태에 따라 달라요. 마감이면 "모집이 마감됐어요" 안내, 비로그인이면 "로그인하면 신청할 수 있어요" 안내와 로그인 링크, 그 외에는 작성 폼을 보여줘요. 상세에서 마감·다시 모집을 누르면 바로 바뀌어요.
- 내 댓글에만 수정(그 자리에서 고치기)·삭제(confirm) 버튼이 있어요. 버튼 글자는 "수정"/"삭제"지만 접근 이름은 "댓글 수정"/"댓글 삭제"라서 모집글의 "삭제" 버튼과 구분돼요.

## 4. 주요 결정과 이유

| 결정 | 이유 |
|---|---|
| **로그아웃 토큰을 서버 메모리(블랙리스트)에 저장** (`TokenBlacklist`, `ConcurrentHashMap<토큰, 만료 시각>`) | 명세가 저장 방식을 자유로 두었고, 테이블을 늘리지 않고 단순하게 가려고요. 새 토큰을 등록할 때 만료된 항목을 함께 지워서 스케줄러 없이도 메모리가 계속 늘지 않아요. **한계**: 서버를 재시작하면 목록이 사라져서, 로그아웃한 토큰을 만료 전까지 다시 쓸 수 있어요. |
| **`user` 테이블 이름을 백틱으로 감싸기** (`@Table(name = "\`user\`")`) | `user`는 MySQL 예약어라 그대로 쓰면 SQL 오류가 날 수 있어요. 이름을 `users`로 바꾸는 대신 ERD 이름을 그대로 지켰어요. |
| **목록 검색은 JPQL `@Query`** | 필터 3개를 조합하는 정도라 쿼리 하나로 충분해요. QueryDSL처럼 의존성이나 빌드 설정을 늘리지 않고, Specification보다 읽기 쉬워요. 정렬은 쿼리에 고정했어요(최신순, 같은 시각이면 id 역순). |
| **댓글은 서비스에서 일괄 삭제** (`@Modifying` JPQL `delete`) | JPA `cascade = REMOVE`는 모집글에 댓글 컬렉션(양방향)이 필요하고, 댓글을 하나씩 조회해 지워요. 일괄 삭제는 DELETE 한 번으로 끝나요. DB `ON DELETE CASCADE`는 `ddl-auto: update`가 기존 FK를 바꾸지 못할 수 있어서 쓰지 않았어요. |
| **`isAuthor`를 `Boolean`(래퍼)으로 선언** | `boolean isAuthor` + Lombok `@Getter`면 getter가 `isAuthor()`가 돼요. 그러면 Jackson이 JSON 이름을 `author`로 만들어 작성자 객체 `author`와 충돌해요. `Boolean`이면 `getIsAuthor()`가 만들어져 명세대로 `"isAuthor"`로 나가요. JSON 테스트로 고정해 뒀어요. |
| **날짜에 `@JsonFormat("yyyy-MM-dd'T'HH:mm:ss")`** | 기본 직렬화는 마이크로초까지 붙어서 명세(`2026-11-08T12:00:00`)와 달라요. |
| **404·405 공통 처리** (`COMMON-005`, `COMMON-006`) | 기존 catch-all `Exception` 핸들러가 없는 URL과 지원하지 않는 메서드까지 500으로 바꾸고 있었어요. 명세 표에 없는 코드라 명세 변경 기록에 남겼어요. 단, 토큰 없이 없는 URL을 부르면 Security가 먼저 401을 내려요(보호 경로를 넓히지 않으려고 이 순서를 유지했어요). |
| **잘못된 쿼리·경로 값은 400** | `?status=FOO`, `/api/study-posts/abc`, `size=0`처럼 변환·검증에 실패하면 `INVALID_INPUT`(`COMMON-003`)으로 내려요. 원래는 500이었어요. |
| **목록 `size` 1~100 제한** (모집글 기본 10, 댓글 기본 20) | 명세에는 기본값만 있어서, 한 번에 너무 많이 가져오지 않도록 상한을 정했어요. 명세 변경 기록에 적었어요. |
| **토큰은 localStorage에 저장** | 새로고침하거나 탭을 다시 열어도 로그인이 유지되고, E2E에서 로그인 상태를 만들기 쉬워요. XSS에 노출되면 토큰이 읽힐 수 있다는 점은 감수했어요(토큰 하나만 쓰는 구조라 메모리 저장은 새로고침마다 로그아웃돼서 불편해요). |
| **URL의 `page`는 1부터** | 주소를 보는 사람에게 `?page=1`이 첫 페이지인 게 자연스러워요. API를 부를 때만 1을 빼서 보내요. |
| **검색은 버튼·Enter로 적용** | 글자마다 요청이 나가지 않고, E2E에서 타이밍이 예측돼요. |
| **댓글은 "더 보기"로 이어 붙이기** | 신청 댓글은 대화처럼 이어서 읽는 게 자연스러워요. 내가 지운 뒤 더 보기를 누르면 페이지 경계가 밀려 댓글이 빠질 수 있어서, 그때는 앞 페이지도 다시 받아 id로 중복을 걸러요. |
| **E2E가 만든 모집글은 테스트가 끝나면 API로 삭제** | 로컬 DB에 테스트 글이 쌓이면 목록 화면이 지저분해져요. 글을 지우면 댓글도 함께 지워져요. 회원 탈퇴 API가 없어서 `e2e-` 계정은 남아요. |
| **E2E 비밀번호는 실행할 때 생성** (`crypto.randomUUID()`) | 테스트 계정이라도 비밀번호를 코드에 고정해 두지 않으려고요. |
| **E2E는 `workers: 1`, 매번 새 계정·제목** | 모든 테스트가 같은 로컬 DB를 써서 한 번에 하나씩 돌리고, 서로의 데이터나 실행 순서에 기대지 않게 했어요. |

| `auth.spec.ts` | 가입 → 로그인 → 헤더 닉네임 → 마이페이지 기수·파트 → 로그아웃 | 중복 이메일, 기수 0(+API 400), 틀린 비밀번호, 로그인 없이 마이페이지(+API 401) |
| `study-post.spec.ts` | 작성 → 검색·상태·파트 필터(새로고침 유지) → 상세 → 수정 → 마감 → 삭제 | 로그인 없이 작성(+API 401), 남의 글 수정·삭제·마감 불가(+API 403 `STUDY-002`) |
| `comment.spec.ts` | 작성 → 그 자리 수정 → 삭제 | 비로그인 안내, 마감 글 댓글 불가(+API 409 `STUDY-003`), 남의 댓글 수정·삭제 불가(+API 403 `COMMENT-002`) |

- 화면에서 숨긴 동작은 버튼이 안 보이는지와 API를 직접 불렀을 때 서버가 막는지를 둘 다 확인해요.
- 각 테스트를 두 번씩 반복 실행(`--repeat-each=2`)해도 24개 모두 통과해서, 테스트끼리 영향을 주지 않는 걸 확인했어요.
