# 개발·협업 컨벤션

## 문서 목적

코드 작성, API 설계, 환경설정, 검증, Git 협업의 공통 기준을 정리한다.
프로젝트의 현재 구조는 `docs/project-structure.md`를 참고한다.

이 문서는 앞으로 적용할 개발 기준을 포함한다.
기존 코드와 차이가 있으면 변경 목적과 영향 범위를 검토하고,
작업과 관계없는 일괄 변경은 피한다.

## 코드 구성과 명명

- 기본 패키지는 `com.cotato.backend14th`를 사용한다.
- 기능별 코드는 `domain/도메인명` 아래에 배치한다.
- 공통 설정·응답·예외 처리는 `global`에 배치한다.
- 클래스는 PascalCase, 메서드와 변수는 camelCase, 상수는 UPPER_SNAKE_CASE로 작성한다.
- 이름은 역할과 의도를 드러내도록 정하고, 의미가 불분명한 축약어는 피한다.
- 기존 코드의 형식을 따르고, 불필요한 포맷 변경으로 변경 범위를 늘리지 않는다.

## 계층별 책임

| 구성요소 | 책임 |
|---|---|
| Controller | HTTP 요청 수신, 입력 검증 연결, 처리 호출, 응답 구성 |
| 요청·응답 DTO | API에서 주고받는 데이터 표현 |
| Service | 업무 로직과 필요한 트랜잭션 경계 관리 |
| Entity | 영속 데이터와 관련 상태·행위 표현 |
| Repository | DB 조회·저장 |

업무 로직이나 여러 데이터 변경을 하나의 트랜잭션으로 처리해야 하면
Service 계층으로 분리한다.

현재 Service가 없는 단순 API를 별도 목적 없이 일괄 개편하지 않는다.
새 기능의 복잡도와 요구사항을 기준으로 책임을 배치한다.

## API 설계

### 요청과 응답

- 요청 DTO와 응답 DTO를 구분한다.
- Entity를 API 응답으로 직접 반환하지 않는다.
- 새 API의 성공 응답은 `ApiResponse`와 `ResponseUtils`를 사용한다.
- HTTP 상태 코드는 처리 결과의 의미에 맞게 선택한다.
- 조회 성공은 200, 리소스 생성 성공은 201을 기본으로 한다.
- 기존 API의 응답 형식을 변경할 때는 이를 사용하는 쪽에 미칠 영향을 확인한다.

### 입력 검증

- 요청 필드의 필수 여부, 길이, 허용 범위는 요구사항을 기준으로 정한다.
- DTO의 검증 어노테이션을 적용하면 Controller에서 `@Valid` 등으로 검증이 실행되도록 연결한다.
- 형식 검증과 업무 규칙 검증을 구분한다.
- 정상 입력뿐 아니라 누락·잘못된 값 등 주요 실패 사례도 확인한다.

### 예외 처리

- 업무상 실패는 `ErrorCode`와 `Backend14thException`으로 표현한다.
- 오류 코드와 메시지는 실패 원인을 구분할 수 있도록 정의한다.
- 예외의 공통 HTTP 응답 변환은 `GlobalExceptionHandler`에서 담당한다.
- 새 실패 유형을 추가하면 의도한 HTTP 상태와 `ErrorResponse`가 반환되는지 확인한다.
- 예외를 잡아 무시하거나 실패를 성공 응답으로 숨기지 않는다.
- 사용자 응답에 비밀번호·토큰·내부 접속정보·스택 트레이스를 노출하지 않는다.

### API 문서

- Swagger 어노테이션으로 API의 목적과 필요한 파라미터를 설명한다.
- 요청·응답과 주요 오류 상황을 실제 동작에 맞게 문서화한다.
- API 계약이 바뀌면 관련 문서도 같은 작업에서 갱신한다.

## 데이터와 트랜잭션

- 생성·수정 시각을 관리하는 Entity는 기존 `BaseEntity`를 활용한다.
- 여러 데이터 변경이 함께 성공하거나 실패해야 하면 트랜잭션 경계를 명확히 한다.
- 트랜잭션 처리가 필요하면 Service 계층에 두는 것을 기본으로 한다.
- 데이터 삭제와 스키마 변경은 영향 범위와 복구 방법을 확인한다.
- 로컬 개발용 JPA 설정을 운영 환경에 그대로 적용하지 않는다.

## 환경설정과 민감정보

- 환경별로 달라지는 값은 환경변수와 프로필 설정으로 분리한다.
- 프로필별 설정은 `application-{profile}.yml`로 구분한다.
- DB 비밀번호·토큰 등 실제 비밀값을 코드에 하드코딩하지 않는다.
- `.env`는 Git에 커밋하지 않는다.
- 문서·테스트 데이터·로그·스크린샷·PR에도 실제 비밀값을 포함하지 않는다.
- 설정 예시에는 실제 값 대신 설명용 값을 사용한다.
- 보안·CORS·의존성 변경은 필요한 범위에서 수행하고 이유를 설명한다.

## 검증

- 변경한 기능과 위험에 맞는 테스트와 수동 확인을 수행한다.
- 업무 로직 변경에는 정상 동작과 주요 실패 사례를 검증하는 테스트를 함께 검토한다.
- 버그 수정에는 가능하면 같은 문제가 재발했을 때 실패하는 테스트를 추가한다.
- 빌드 성공, 서버 시작, DB 연결, Swagger 접속, 개별 API 동작을 서로 구분한다.
- 검증 결과는 통과·실패·미확인으로 기록하고, 미실행 항목은 이유를 남긴다.
- 실행하지 않은 검증을 통과했다고 기록하지 않는다.

### 기본 명령어

Windows PowerShell:

```powershell
.\gradlew.bat build
.\gradlew.bat test
.\gradlew.bat bootRun
```

macOS·Linux:

```bash
./gradlew build
./gradlew test
./gradlew bootRun
```

`build`는 기본 테스트를 포함한다.
같은 변경에 대해 `build`가 성공했다면 특별한 이유 없이 `test`를 다시 실행하지 않아도 된다.

애플리케이션과 DB를 사용하는 테스트는 로컬 환경설정과 DB 실행이 필요할 수 있다.

## Git 협업

### 브랜치

- 개인 누적 브랜치는 `영문이름/basic` 형식으로 관리한다.
- 작업 브랜치는 개인 누적 브랜치에서 분기하고, PR도 해당 누적 브랜치를 대상으로 한다.
- 작업 브랜치의 구체적인 이름은 해당 작업의 협업 안내를 따른다.
- 브랜치를 전환하기 전에 커밋하지 않은 변경사항을 확인한다.
- `main`과 `develop`에 직접 push하지 않는다.
- 강제 push를 사용하지 않는다.

### 커밋

커밋 메시지는 `타입: 작업 내용` 형식으로 작성한다.

| 타입 | 용도 |
|---|---|
| feat | 기능 추가 |
| fix | 오류 수정 |
| docs | 문서 작성·수정 |
| style | 기능 변경 없는 형식 정리 |
| refactor | 기능 변경 없는 구조 개선 |
| chore | 설정·의존성 등 기타 작업 |

- 관련 변경을 의미 있는 단위로 묶는다.
- 메시지에는 실제 변경 내용을 구체적으로 적는다.
- 커밋 전 변경 파일과 내용을 확인한다.
- 민감파일, 빌드 산출물, 개인 IDE 설정이 포함되지 않도록 한다.

### 이슈와 PR

- 작업 목적과 완료 조건을 이슈에 정리한다.
- PR에는 변경 내용, 이유, 검증 결과, 리뷰가 필요한 사항을 적는다.
- 별도의 제출 형식이 있으면 해당 형식을 따른다.
- 이슈를 해결하는 PR은 `closes #이슈번호`로 연결한다.
- 제출 전에 base와 compare 브랜치를 확인한다.
- PR은 파트장의 검토 후 머지한다.

## 문서 유지

- 구조가 변경되면 `docs/project-structure.md`를 갱신한다.
- 개발 기준이 변경되면 이 문서와 관련 Rule을 함께 검토한다.
- 기능 개발 PR의 상세 기록은 `docs/features/이슈번호-작업명.md`에 작성한다.
- 같은 내용을 여러 문서에 복사하기보다 기준 문서를 정하고 참조한다.

## Hook 실행 환경

- 강제 push 차단 Hook은 Bash와 jq가 필요하다.
- `.claude/settings.json`의 Git Bash 경로는 설치 환경에 맞게 조정한다.
- Hook은 명령 문자열의 패턴을 검사하는 보조 안전장치다.
- 별칭·변수로 조립한 명령·외부 스크립트 내부는 검사하지 않는다.
- 복잡한 인용문이나 옵션 값에서 오탐할 수 있다.
