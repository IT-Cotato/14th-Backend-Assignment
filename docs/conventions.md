# 협업 컨벤션

## 브랜치

| 브랜치 | 용도 |
| --- | --- |
| `develop` | 레포의 default 브랜치. 4주차부터는 `이름/basic`을 처음 만들 때 기준으로만 쓰고, 이후 작업·PR에는 쓰지 않는다. 직접 push 금지 |
| `이름/basic` | 4주차부터 쓰는 내 누적 브랜치. 직접 push 금지, PR로만 반영 |
| `이름/harness`, `이름/monorepo` 등 | 주차별 작업 브랜치. 여기서 작업 후 `이름/basic`으로 PR |
| `feat/이슈번호-기능명`, `fix/이슈번호-버그명` | 1~3주차 방식(지금은 쓰지 않음). 당시에는 `develop`으로 PR |

- `main` 브랜치는 이 레포에 없다.

- 이름은 영문 소문자로 쓴다. (예: `gildong/basic`)
- `이름`만으로 된 브랜치는 만들지 않는다. (`이름/basic`과 충돌)
- 작업 시작 전에 기준 브랜치를 pull 받는다.

```bash
git checkout 이름/basic
git pull origin 이름/basic
git checkout -b 이름/작업명
```

## 커밋 메시지

형식: `타입: 작업 내용 요약`

| 타입 | 의미 |
| --- | --- |
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서 수정 |
| `style` | 코드 포맷 등 기능 변경 없음 |
| `refactor` | 기능 변경 없이 코드 구조 개선 |
| `chore` | 빌드 설정, 의존성, 하네스 설정 등 기타 작업 |

- 좋은 예: `feat: 지원자 단건 조회 API 추가`, `chore: .gitignore에 .env 추가`
- 나쁜 예: `수정함`, `fix`, `ㅇㅇ됨`
- 한 커밋에는 한 가지 목적만 담는다.

## 이슈

- 레포에 등록된 이슈 템플릿(📌 Description / ✅ To-do / 📒 기타)을 그대로 쓴다.
- 제목: `타입: [이름] 작업 요약` (예: `chore: [홍길동] 4주차 하네스 구축`)

## PR

- 제목: `타입: [이름] 작업 요약 (closes #이슈번호)`
- 본문: 개요 / 작업 내용 / 관련 이슈(`closes #N`) / 리뷰 포인트
- **base 브랜치를 꼭 확인한다.** 4주차부터는 `이름/작업 → 이름/basic`이다. GitHub는 default인 `develop`을 base로 잡으므로 반드시 바꾼다.
- 머지는 파트장이 한다.
- PR마다 `docs/features/이슈번호-작업명.md` 기능 문서를 1개 작성한다. (5주차부터)

## 코드 리뷰

- 제안하는 말투로 남긴다. ("~하면 어떨까요?")
- 줄 단위 코멘트는 `Submit review`를 눌러야 전달된다.
- 볼 것: 네이밍, 남은 디버그 코드, 컨벤션 준수 여부
